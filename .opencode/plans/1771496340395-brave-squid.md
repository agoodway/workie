# Autopilot Backend Selection Plan (Claude Code or Codex)

## Goal
Add backend selection for `workie autopilot` so users can run with either Claude Code or Codex, using:
- `--backend` CLI override
- `.workie.yaml` fallback
- backend-specific default model when `--model` is not explicitly set

User-confirmed behavior:
- Selection UX: flag + config fallback
- Flow/prompt behavior: unchanged (same phases and prompt content), only execution backend changes

## Recommended Implementation

### 1) Add backend + autopilot config shape
Update config schema to support autopilot defaults:
- Add `Autopilot *AutopilotConfig` to `Config`
- Add:
  - `AutopilotConfig.Backend string`
  - `AutopilotConfig.Models map[string]string`

Expected YAML shape:
```yaml
autopilot:
  backend: codex
  models:
    claude: opus
    codex: gpt-5-codex
```

Notes:
- Keep parsing permissive (no heavy validation in `config.LoadConfig`)
- Validation and normalization happen in autopilot command/pipeline layer

### 2) Add backend selection to CLI
In `workie autopilot` command:
- Add `--backend` flag (`claude|codex`)
- Update help text to backend-neutral wording (e.g., `--model` is no longer “Claude model”)
- Resolve effective backend/model with precedence:
  - Backend: `--backend` (if changed) > config `autopilot.backend` > `claude`
  - Model: `--model` (if changed) > config `autopilot.models.<backend>` > backend default

Important compatibility rule:
- Detect explicit user input with `cmd.Flags().Changed("backend")` and `cmd.Flags().Changed("model")`
- This prevents `--model`’s legacy default (`opus`) from overriding Codex defaults when user did not set model intentionally

### 3) Introduce backend adapter in autopilot package
Create a small backend abstraction dedicated to command construction:
- Parse/validate backend string (`claude`, `codex`)
- Resolve backend default model
- Build process invocation details (binary + args) per backend

Recommended command mapping:
- Claude backend:
  - binary: `claude`
  - args base: `--print --model <model>`
  - `--show-output`: add `--verbose`
  - `--auto-approve`: add `--dangerously-skip-permissions`
- Codex backend:
  - binary: `codex`
  - args base: `exec --model <model>`
  - `--auto-approve`: map to `--full-auto`
  - `--show-output`: keep Go-side stream behavior; no extra Codex verbose flag required initially

### 4) Make pipeline execution backend-agnostic
Refactor `autopilot/pipeline.go` minimally:
- Add `Backend` field to `PipelineOptions`
- Replace Claude-specific executor calls with generic executor using backend adapter
- Keep all orchestration logic unchanged:
  - phase ordering
  - prompt generation
  - multi-change behavior
  - intermediate commit behavior

Logging/output updates:
- Include backend in banner/debug logs
- Dry-run text should say selected backend command, not always `claude`
- Error messages should identify backend (`codex session failed...`, etc.)

### 5) Backend-aware preflight and hints
Keep preflight structure but make checks backend-specific:
- Verify selected binary is available (`exec.LookPath`)
- Run preflight prompt through selected backend with timeout
- Return backend-specific guidance in failures:
  - Missing binary: install/check PATH
  - Codex auth failures: suggest `codex login`
  - Keep current Claude MCP hang hint on Claude path

## Verification Plan

### Automated tests
Run:
```bash
go test ./config ./autopilot
```

Test coverage to add:
- Config parsing:
  - `autopilot.backend`
  - `autopilot.models` map
- Backend adapter:
  - valid/invalid backend parsing
  - default model resolution per backend
  - arg construction for Claude vs Codex with `--auto-approve` and `--show-output`
- Pipeline option validation:
  - invalid backend rejected
  - empty model rejected
  - existing phase validation still enforced

### End-to-end smoke checks
Run from repo root with a known change name:
```bash
workie autopilot <change> --backend claude --dry-run
workie autopilot <change> --backend codex --dry-run
```

Then verify config fallback + override:
1. Set `.workie.yaml` `autopilot.backend: codex`, run without `--backend`, confirm banner/log shows codex
2. Run with `--backend claude` and confirm CLI flag overrides config

### MCP/tools behavior
- No MCP tool contract changes are planned
- Existing phase prompts and slash-command workflow remain unchanged for both backends
- Validate preflight still catches early backend startup failures before phase execution

## Risks and Mitigations
- Model default mismatch when switching backend
  - Mitigation: use `Flags().Changed("model")` and backend default resolution
- Backend CLI arg drift over time
  - Mitigation: isolate mapping in single adapter file + unit tests
- Sparse existing autopilot tests
  - Mitigation: add pure-function adapter tests and focused pipeline validation tests first
